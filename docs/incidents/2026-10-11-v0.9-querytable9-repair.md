# Incident: v0.9_working opens with "Removed Part: /xl/queryTables/queryTable9.xml"

**Logged:** 11 October 2026 · **Status:** **closed**. Fixed in the rebuild of 11 October 2026. The user's rebuilt copy opened and ran Load Project in desktop Excel without a repair prompt.
**Reported by:** user, opening the v0.9 package workbook from SharePoint in desktop Excel on a work PC

## Symptom

Excel opened `Clinical_Research_Cash_Flow_SharePoint_PQ_Ready_v0.9_working.xlsm` from the SharePoint folder `04 Outputs Repository/Project Tracking System`, said it had to make repairs, and logged this:

```
Removed Part: /xl/queryTables/queryTable9.xml part. (External data range)
```

## What queryTable9 is

`xl/queryTables/queryTable9.xml` (`ExternalData_3`, connection 9 "Query - qManpower_SelectedTest") links the manpower selected-test table to its Power Query query. The table is `xl/tables/table15.xml` on sheet 14.

- v0.8: table `qManpower_SelectedTest` on sheet `PQManpower_SelectedTest`.
- v0.9: renamed to table `tblManpowerSelectedTest` on sheet `PQ_Manpower_SelectedTest`, at the user's request in the build session.

## Root cause (confirmed)

### 1. The hidden name for the external data range still points at the old sheet name (definite defect)

Every Power Query table has a hidden defined name that tells Excel which cells the query table fills. In `xl/workbook.xml`:

| | Defined name | Refers to | Sheet exists? |
|---|---|---|---|
| v0.8 | `ExternalData_3` (localSheetId 13) | `PQManpower_SelectedTest!$A$1:$R$13` | yes |
| v0.9 (build output and shipped file) | `ExternalData_3` (localSheetId 13) | `PQManpower_SelectedTest!$A$1:$R$13` | **no**: the sheet is now `PQ_Manpower_SelectedTest` |

`build/build_v09_working.py` renamed the sheet in `workbook.xml` (`<sheet name=…>`) and in `docProps/app.xml`, but **not inside the defined-name formulas**. `ExternalData_3` was left pointing at a sheet that no longer exists. Excel can't place query table `ExternalData_3`, treats `queryTable9.xml` as corrupt, and removes it.

Evidence: a fresh rebuild from v0.8 with the current script reproduces the dangling name. `PQManpower_SelectedTest` appears nowhere else in the package except the Power Query DataMashup.

### 2. Power Query's saved load target still names the old table (likely contributor)

The DataMashup metadata for `Section1/qManpower_SelectedTest` records `FillTarget = qManpower_SelectedTest` and `FillTargetNameCustomized = 1`. The build left the DataMashup byte-identical by design, so after the XML-only rename the query's load target names a table that no longer exists. When a table is renamed in the Excel UI, Excel keeps the defined name and `FillTarget` in step; renaming by editing XML does neither. Even with cause 1 fixed, this mismatch could cause the same repair, or a broken refresh.

### Why only queryTable9

It's the only table and sheet that was renamed. The other nine query tables kept their names, and Excel accepted them.

## Contributing factors

- ~~The shipped workbook isn't the verified build output (re-saved by Excel iOS).~~ **Corrected in the fix session:** the shipped `.xlsm` *was* the build output. Every part not meant to change, including all ten query tables and `vbaProject.bin`, is byte-identical to the v0.8 uploaded for the fix. It reports "Excel iOS" because v0.8 does: the builder copies `docProps/app.xml`, and **v0.8 itself was last saved by Excel for iPhone/iPad**. The placeholder-style IDs (`{00000000-0016-…}`) are in v0.8 too. So this was not a cause, but see "v0.8 baseline" under Resolution.
- **The verifier had a blind spot.** `verify_v09_working.py` exempted the manpower table part from the byte-identical check ("except the manpower table rename"). It didn't check that defined names point at existing sheets, or that each query table's name matches its query's `FillTarget`. So it reported PASS on a broken file.

## Impact

- In the repaired copy, `tblManpowerSelectedTest` is a **plain table that no longer refreshes**: the link to `qManpower_SelectedTest` is gone. Load Project would fail on the manpower refresh, or show stale manpower data.
- v0.8 is unaffected. Source workbooks are unaffected. The query definitions (M code) are intact.
- **Don't use or save the repaired copy.** If AutoSave already wrote it back to SharePoint, that copy is to be replaced with a rebuilt file. Don't overwrite v0.8.

1. **Recommended: drop the rename from the build.** Keep the v0.8 names (`qManpower_SelectedTest`, sheet `PQManpower_SelectedTest`). The defined name, `FillTarget` and query table then all agree, with zero Power Query drift. 2. Alternative (riskier, only if the user insists on scripted names): also rewrite `ExternalData_3` to the new sheet name, and patch the DataMashup metadata `FillTarget` → `tblManpowerSelectedTest`. That means re-encoding the DataMashup binary, which the project has so far kept byte-identical.

4. **Rebuild from v0.8** and run the verifier. Repackage the zip from the **exact build output**, and record a SHA-256 in `README_FIRST.txt`.
5. **Tell the user:**
   - download on the work PC and open **only in desktop Excel for Windows**;
   - don't open it in Excel on a phone, tablet or the web before the macros are installed;

## Resolution (11 October 2026)

1. **Rename dropped** (fix plan option 1). `build/build_v09_working.py` no longer renames the table or sheet; they keep the v0.8 names `qManpower_SelectedTest` / `PQManpower_SelectedTest`. `ExternalData_3`, `queryTable9`, `table15` and the `FillTarget` all agree, and every Power Query part is byte-identical to v0.8. The VBA reads the table name from one constant, `modTimeline.MANPOWER_TABLE`. `compare_pq.py`, `tests/grid_model.py`, the spec (v1.0.2) and the docs use the v0.8 names.
2. **Verifier hardened.** `verify_v09_working.py` has no exemptions and runs `check_links` on both files:
   - every part parses and has a content type; every relationship target exists;
   - every sheet named in a defined name exists, and each `ExternalData_n` sits on the sheet its formula names;
   - structured references name existing tables; table names and ids are unique;
   - sheet → table → queryTable → `ExternalData_n` (same sheet and range) → connection → query → DataMashup `FillTarget` agree, and each loading query has exactly one table.
   On the first (shipped) v0.9 it reports three problems: `ExternalData_3` points at a missing sheet, sits on a different sheet from the one it names, and `FillTarget` is `qManpower_SelectedTest` for table `tblManpowerSelectedTest`. On v0.8 and the rebuild it reports none. `compare_pq.py` (acceptance test 13) runs the same link check on the Excel-saved file.
3. **Rebuilt** from the uploaded v0.8 (SHA-256 `db3bdd5b1a3cf6182309b63748522959946baa1ec96c5bb303cd370b1dc81ab0`). Verifier, `compare_pq.py` and `tests/grid_model.py` (34 checks, LibreOffice recalculation of a scratch copy) all pass. The package zip holds the exact build output; its SHA-256 is in `README_FIRST.txt`, and `release/CashFlow_v0.9_package.zip` is replaced.
4. **Build input guard.** The fix session's first draft refused any v0.8 not last saved by desktop Excel. That would refuse the real baseline, so the builder now prints which app last saved the input and relies on the verifier's link checks instead.

**v0.8 baseline.** The uploaded v0.8 reports `Application = Excel iOS`, so it was last saved on an iPhone or iPad (possibly by AutoSave while viewing it on SharePoint). Its Power Query and VBA parts pass every check, so it's usable. The user may want to check v0.8's SharePoint version history and avoid opening it in the Excel mobile app while signed in with AutoSave on.

**Confirmed (11 Oct 2026):** the user's rebuilt copy (v0.8 manpower names) opened, refreshed and loaded in desktop Excel with no repair prompt. *Original note:* only desktop Excel can prove the fix. The user opens the rebuilt file in desktop Excel for Windows; no repair prompt closes this incident. If a repair prompt still appears, capture the full repair log (the "View" link, or the XML log under `%TEMP%`) and reopen.

## Prevention

- **Never rename sheets or tables that Power Query loads by editing XML.** Rename them in the Excel UI, or not at all.
- The verifier checks cross-part references (defined names, query-table ↔ table ↔ FillTarget), not just byte equality.
- Ship only files whose hash matches the build output.
